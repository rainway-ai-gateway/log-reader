# LR04 MySQL 启动连接失败后台重试场景（scenario-LR04-mysql-startup-connect-retry）

## 场景概述

验证 `mod_log_mysql` 的连接容错：MySQL（`bfe_report`）不可达时 log-reader **不退出**，后台持续重试；断连期间日志入队缓冲；MySQL 恢复后自动建连并排空积压。同时守护 fail-fast 分界——配置错误（如 `Mysql.Addr` 为空）仍立即退出。覆盖两种断连形态：启动不可达（TC-04-01）与运行期断连（TC-04-03，二期自动重连）。

修改设计见 `doc/modifications/2026-09-29-mod-log-mysql-startup-connect-retry/design-changes.md`（一期）与 `doc/modifications/2026-09-30-mod-log-mysql-runtime-reconnect/design-changes.md`（二期）。

## 被测进程与配置

- **被测进程**：真实 `log-reader` 二进制，`Modules = mod_log_mysql`，`-b` 从文件头读取；monitor 端口由测试预先占用（`common.FreePort`）并经 `{{HTTP_PORT}}` 注入 `config.conf`（`StartLogReaderOnPort`），供测试轮询 `/monitor/mod_log_mysql`。
- **MySQL 不可达模拟**：testcontainers 启动 `mysql:8.0` → 建库 → 应用 DDL → `common.MysqlEnv.Pause`（Docker `ContainerPause` 冻结容器进程；新连接 TCP 挂起）。恢复用 `Unpause`。外部 `LR_MYSQL_DSN` 后端无法 Pause/Unpause，TC-04-01 调用即 `t.Skip`。
- **建连配置**（`testdata/mod_log_mysql/mod_log_mysql.conf`）：`ConnectTimeoutMs = 2000`、`ConnectRetryIntervalMs = 200`，使重试循环在测试时间内可观测；`BatchTimeoutMs = 2000`（单批事务超时，TC-04-03 DOWN 窗口的上界决定项，见二期设计 §4.2⑥）。
- **harness 扩展**：`ProcessEnv.StartLogReaderEx/OnPort`（进程退出探测 `waitExit`）、`common.FetchMonitor/WaitMonitor`（monitor JSON 抓取，`MYSQL_CONN_STATE` 等键值只能经 HTTP 观测）。

## 关键断言点

- **进程存活**是本改动核心：`waitExit` 在 MySQL 不可达时必须返回 `exited=false`（改动前行为为 `Exit(1)`）。
- **观测通道**：`MYSQL_CONN_STATE`/`MYSQL_CONN_RETRY`/`MYSQL_CONN_OK`/`MYSQL_CONN_LOST`/`SENT_TO_MYSQL`/`WRITE_BATCH_SIZE`/`SEND_MYSQL_FAILED` 经 `/monitor/mod_log_mysql`（默认 JSON：`States`/`SCounters` 两个 map）。
- **恢复闭环**：Pause 状态新连接 TCP 挂起而非拒绝，TC-04-01 同时覆盖 `PingContext` 超时路径（`ConnectTimeoutMs` 生效）；TC-04-03 覆盖写路径超时（`BatchTimeoutMs` 生效）。
- **断连期背压语义**：`SENT_TO_MYSQL`（入队）增长、`WRITE_BATCH_SIZE`（实际写库）停滞。
- **二期对照**：TC-04-03 断言 `SEND_MYSQL_FAILED=0`——运行期断连不再线性丢批（一期行为：每分钟约丢 30 批）。
