# TC-04-01 启动不可达后台重试与恢复补写

## 用例编号与名称

TC-04-01 启动不可达后台重试与恢复补写（`TestLR04_StartupMysqlDownThenRecover`）

## 所属场景

LR04 MySQL 启动连接失败后台重试场景（scenario-LR04-mysql-startup-connect-retry）

## 版本声明

- `log-reader`：v1.5.0-dev 起（`mod_log_mysql` 启动连接容错改造后）

## 测试目的

验证 `mod_log_mysql` 启动时 MySQL（`bfe_report`）不可达的新行为：

1. log-reader **不退出**，进程与 WebServer/monitor 正常可用（改动前行为为 `Exit(1)`）；
2. 模块后台按 `ConnectRetryIntervalMs` 持续重试，`MYSQL_CONN_STATE=DOWN` 且 `MYSQL_CONN_RETRY` 持续增长；
3. 断连期间到达的日志**入队缓冲**（`SENT_TO_MYSQL` 增长、`WRITE_BATCH_SIZE` 为 0），不丢、不写库；
4. MySQL 恢复后**自动建连**（`STATE=UP`、`MYSQL_CONN_OK=1`），积压自动排空补写，落库行与日志一一对应（幂等）。

同时覆盖 `PingContext` 超时路径：Pause 状态下新连接 TCP 挂起而非拒绝，单次建连受 `ConnectTimeoutMs` 约束。

## 运行模式

单组件模式：真实 `log-reader` 进程 + testcontainers `mysql:8.0` 容器（需本机 Docker）。MySQL 不可达与恢复通过 Docker `ContainerPause`/`ContainerUnpause` 模拟。

**环境约束**：仅 testcontainers 后端可运行；`LR_MYSQL_DSN` 外部实例无法 Pause/Unpause，用例 skip。无 Docker 且无 DSN 时同样 skip（`MysqlEnv` 前置跳过）。

## 前置条件

- 本机 Docker 可用（testcontainers 启动 `mysql:8.0`）；
- 自动编译的 `log-reader` 二进制（首次运行缓存至 `tests/integration/.integration-test-bin/`）。

## 配置构造

- `config.conf`：`Modules = mod_log_mysql`，`-b` 从文件头读取；monitor 端口由测试预占（`common.FreePort`）并经 `{{HTTP_PORT}}` 注入——LR04 需在建配置前知道端口，以便轮询 `/monitor/mod_log_mysql`（默认 JSON：`States`/`SCounters` 两个 map）。
- `mod_log_mysql/mod_log_mysql.conf`：指向被 Pause 的容器地址；`ConnectTimeoutMs = 2000`、`ConnectRetryIntervalMs = 200`（缩小超时/间隔使重试循环在测试时间内可观测）；`QueueSize = 2000`、`BatchSize = 5`、`FlushIntervalMs = 200`。
- 表结构：testdata 内嵌 DDL 副本 `testdata/ddl/bfe_ai_request_log.sql` 初始化（与 LR03 同源）。

## 输入数据

3 条 request 类型日志（`common.MakeRequestLog`），logid 40001–40003、模型互不相同（唯一键互不冲突）：

| logid | host | uri | ai_requested_model |
|-------|------|-----|--------------------|
| 40001 | retry.example.org | /v1/chat | retry-model-a |
| 40002 | retry.example.org | /v1/chat | retry-model-b |
| 40003 | retry.example.org | /v1/embed | retry-model-c |

写入时机：log-reader 已启动且确认进入 DOWN 重试状态之后（断连期写入，验证缓冲语义）。

## 操作步骤

1. testcontainers 启动 MySQL → 建库（随机名 `bfe_report_lr03_<ts>`）→ 应用 DDL。
2. `MysqlEnv.Pause` 冻结容器（MySQL 不可达：新连接 TCP 挂起）。
3. 生成配置（monitor 端口预占注入）→ 启动 log-reader（`-b`）。
4. `waitExit(3s)` 断言进程**未退出**；`/monitor/mod_log_mysql` 可访问。
5. `WaitMonitor` 断言 `MYSQL_CONN_STATE = DOWN`。
6. `WaitMonitor` 断言 `MYSQL_CONN_RETRY` 在 15s 内持续增长（间隔 ≈ 重试间隔 + 单次超时）。
7. 写入 3 条日志；`WaitMonitor` 断言 `SENT_TO_MYSQL = 3` 且 `WRITE_BATCH_SIZE = 0`（入队缓冲、未写库）。
8. `MysqlEnv.Unpause` 恢复容器。
9. `WaitMonitor` 断言 `MYSQL_CONN_STATE = UP`（60s 超时）；断言 `MYSQL_CONN_OK = 1`、`MYSQL_CONN_RETRY >= 1`。
10. `WaitTableCount(bfe_ai_request_log, 3, 60s)` 等待积压排空落库。
11. 查询 `logid BETWEEN 40001 AND 40003` 的 distinct 计数，断言 = 3。

## 预期结果

- 步骤 4：MySQL 不可达时进程存活、monitor 可访问（改动前此处进程已退出）。
- 步骤 5-6：`DOWN` 状态可见，重试计数单调增长（重试循环工作正常）。
- 步骤 7：断连期 3 条日志全部入队（`SENT_TO_MYSQL=3`），无任何写库（`WRITE_BATCH_SIZE=0`）。
- 步骤 9-11：恢复后自动建连并排空，`STATE=UP`、`MYSQL_CONN_OK=1`；表内 3 行、logid 齐全，与输入一一对应。
- 全程进程无 panic、无异常退出；重试日志节流（前 3 次 Error、之后每 10 次一条 Warn，可用 `dumpLogs` 抽查）。

## 清理

停止 log-reader 进程（测试 defer：`stopReader()` → SIGTERM），关闭日志生成器与数据库连接，终止容器并删除测试库，删除临时工作目录。

## 不在本用例范围

运行期断连（已建连后 MySQL 挂掉）：维持原语义（写失败退避重试后丢弃计 `SEND_MYSQL_FAILED`，进程不退出；网络恢复后连接池自行换连接恢复写入），一期手工验证，自动化列二期（Pause 下连接池拨号无超时，断言窗口不稳定，见场景说明）。
