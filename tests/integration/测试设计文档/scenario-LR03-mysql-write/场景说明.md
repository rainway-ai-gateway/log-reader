# LR03 MySQL 写入场景（scenario-LR03-mysql-write）

## 场景概述

验证 log-reader 的 `mod_log_mysql` 模块：读取 protobuf 访问日志，将 AI 请求日志按固定 99 列映射写入 MySQL 明细表 `bfe_ai_request_log`，并保证重发/补读幂等；同时保证**同秒同 API Key 同模型的并发请求各自成行**（幂等键含请求级判别列 `logid`，bfenetworks/bfe#1417）。

与 LR01（Kafka 输出）不同，本场景不依赖 MockKafka，而是向真实 MySQL 写入并直接查询数据库断言行内容。

## 被测进程与配置

- **被测进程**：真实 `log-reader` 二进制，`Modules = mod_log_mysql`，`-b` 从文件头读取。
- **日志来源**：测试代码直接生成 b2log 格式 protobuf 日志（`common.LogGenerator`），与 LR01 相同。
- **MySQL 来源**（`common.MysqlEnv` 按优先级选择）：
  1. 环境变量 `LR_MYSQL_DSN`（格式 `user:pass@tcp(host:port)/dbname`，凭据需具备 CREATE/DROP DATABASE 权限）；测试创建专用随机名数据库（如 `bfe_report_lr03_<ts>`），结束后 DROP，**绝不使用 DSN 中自带的数据库名**；
  2. testcontainers 启动 `mysql:8.0` 容器（需本机 Docker 可用）；
  3. 都不可用则 `t.Skip`。
- **表结构**：testdata 内嵌 DDL 副本 `testdata/ddl/bfe_ai_request_log.sql` 初始化（副本说明见文件头注释；权威 DDL 归 ai-gateway-api 仓库发布后以其为准重新生成，幂等键与权威一致：五列含 `logid`）。
- **写入配置**（`testdata/mod_log_mysql/mod_log_mysql.conf`）：`BatchSize = 5`、`FlushIntervalMs = 200`、`MaxRetries = 3`，读侧 `MaxSizePerBatch = 10`（config.conf），刻意小于用例日志量以覆盖攒批/拆分路径。
- **监控端口**：由 `common.FreePort` 动态分配（配置模板 `config.conf` 的 `httpPort={{HTTP_PORT}}`），避免与其它场景或宿主机端口冲突；需要读取计数器的用例（TC-07）轮询 `/monitor/mod_log_mysql`。

## 关键断言点

- **列映射正确性**：以 `reader_modules/mod_log_mysql/field_mapper.go` 的 99 列清单为基准，抽样覆盖全部列类别（标量/布尔/JSON/标签打平/log_time）。
- **零值规则**：可空字符串列零值→NULL；NOT NULL 字符串列（`ai_cache_status`/`mirror_cluster`/`ai_intent_*` 字符串列）空串原样写入（→''）；数值/布尔零值→原值（0）；三个可空意图数值列（`ai_intent_confidence`/`ai_intent_latency_us`/`ai_intent_cache_hit`）proto 未设置→NULL（=未求值），显式置 0→0。
- **幂等键与覆盖语义**：唯一键为 `(hostid, log_time, ai_apikey_id, ai_requested_model, logid)`（含请求级判别列 `logid`，bfenetworks/bfe#1417）；`INSERT ... ON DUPLICATE KEY UPDATE` 的行为 = **同一请求重放**（同 `logid`）时行数不增、值覆盖（覆盖"重发"与"-b 补读"两种形态）；**不同 `logid` 的并发请求各自成行**（TC-06），修复前四列键下这类请求被全列覆盖折叠为 1 行。
- **时间列**：`log_time` = pb `timestamp`（Unix 秒），以 UTC 比较。
- **数值列范围归一化（issue #12）**：proto `uint32` 值域大于 DDL 列类型，超界值写入前 clamp 到列上限（如 `proxy_delay_time` → `2147483647`）并计数 `VALUE_NORMALIZED`；越界不得产生 MySQL 1264、不得导致同批正常行/401 行丢失（`SEND_MYSQL_FAILED`/`MYSQL_CONN_LOST`/`ROW_DROPPED_DATA` 均不增，TC-07）。

## 实现期间发现并修复的问题

1. **reader_conf 模块白名单遗漏**：`reader_conf/conf_load.go` 的 `modulesSupport` 未加入 `mod_log_mysql`，导致配置加载报 `module[mod_log_mysql] is not support`（单测/编译均无法发现，集成测试发现后已修复）。
2. **参考 DDL 行大小超限**：设计参考 DDL 中 8 个长文本列（origin_uri/final_uri/x_forward_for/authorization/referrer/user_agent/cookie/res_location）使用 VARCHAR，utf8mb4 下总长度超 MySQL 65535 字节行上限（Error 1118），测试副本已改为 TEXT，权威 DDL 需同步。
3. **参考 DDL 幂等键与零值规则冲突**：`ai_apikey_id`/`ai_requested_model` 的 `NOT NULL` 使未认证请求（apikey 为空→NULL）整批写入失败（Error 1048），测试副本已将这两列改为可空；`hostid`/`log_time` 由 log-reader 构造保证非空，保持 NOT NULL。
4. **幂等键粒度丢失明细行（bfenetworks/bfe#1417）**：唯一键原为四列 `(hostid, log_time, ai_apikey_id, ai_requested_model)`，而 `log_time` 是秒级、写入侧又是全列覆盖——同秒同 Key 同模型的并发请求被折叠为 1 行（丢率 (n−1)/n，生产实测窗口 13.5%），且被覆盖行的 tokens/cost 从求和中整体消失。修复方式：BFE 侧保证 `logid` 逐请求唯一非 0（`bfe@89defa14`）+ 权威 DDL 把 `logid` 入键并收紧为 `NOT NULL DEFAULT 0`（`ai-gateway-api@64f278e`）；**本模块写入侧零代码改动**（列清单与覆盖子句均由 `Columns()` 动态生成），本次仅同步测试副本 DDL 并新增 TC-06 回归锁。
